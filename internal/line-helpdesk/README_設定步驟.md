## 2.1 偵錯修正（2026-10-03）

- 修正「痛」「咳」「喘」等單字被當成客套話而忽略；現在會繼續查題庫或轉人工。
- 限縮謝謝類辨識，避免「謝謝但是還痛」的後半句被忽略。
- PENDING_HOURS 的 NaN／無限值／負值／過大值回復 24 小時，0 仍代表不自動恢復。舊案件的無時區日期按 UTC 處理；日期欄位損壞時保留人工接手狀態，避免意外插話。

- LINE HTTP 400 記為發送失敗並停止對同一事件重試；HTTP 429／5xx 仍保留重試。請在 Cloud Run 日誌查 `helpdesk_reply_rejected`，在 Firestore events 查 delivery 欄位。這不代表失敗訊息已送達；若是內容格式錯誤需修正後人工補回覆。
- 忽略 standby 事件；Quick Reply 標籤按 UTF-16 單位裁切，避免表情符號導致超長。按鈕實際傳送的問題保留完整，避免裁切後找不到答案。

## 先保留三個既有自動回覆

目前「流感疫苗資訊」「過敏氣喘諮詢」「減重營養諮詢」由 LINE 官方帳號後台回答。這一版會略過這三個關鍵字，以免重複回覆。

**重要限制：人工接手時，只能停止 Cloud Run 的回答，無法停止 LINE 後台獨立的自動回覆。** 民眾若在等待期間點選這三個按鈕，仍可能收到原本資訊。其他後台預設回應也不受此程式控制。

若要人工期間「所有自動訊息完全停止」，需要先將後台三組內容（包含圖片、卡片、連結）提供並移入 legacy_messages.json，逐一測試後關閉後台自動回應，再把 OA_PASSTHROUGH_KEYWORDS 改成 []。**不要在尚未移入內容時直接關閉三組既有功能。**

## 第一步：確認原服務與備份

1. Google Cloud Console → Cloud Run → 點選目前 LINE Webhook 使用的服務。
2. 留存目前成功版本（revision）名稱、服務網址、執行身分與原程式。不要刪除舊版本。
3. 若是函式編輯器，入口維持 `linebot`，Python 使用 3.12。若是容器服務，本包附 Dockerfile。
4. 原 LINE Token / Secret 使用現有值；不要傳到 ChatGPT，也不要放入公開程式碼。

## 第二步：建立持久化案件資料

1. 同一個 Google Cloud 專案 → Firestore，若尚未有資料庫，建立 Native mode 資料庫。可選鄰近且符合診所資料政策的區域；建立後區域不易變更。
2. 本程式預設使用 `(default)` 資料庫；如果已有其他名稱，填入 `FIRESTORE_DATABASE`。
3. 找到此 Cloud Run 服務真正使用的服務帳戶，在 IAM 授予該帳戶 `Cloud Datastore User` (`roles/datastore.user`)。不要授權 allUsers 或修改整個專案所有人的權限。
4. 使用服務帳戶的內建身分，不必建立或下載 JSON 私鑰。Firestore 不需要開放公共讀寫規則。
5. 程式第一次處理問題時會建立 `lh_helpdesk_sessions` 與 `lh_helpdesk_events` 集合。
6. 在 Firestore TTL 設定中，為 collection group `lh_helpdesk_events` 的 `expires_at` 啟用 TTL，清理七天以上事件記錄。**不要為 sessions 設自動刪除 TTL**，否則未結案件可能被誤恢復。
7. 本包有用量成本：Cloud Run、Firestore 依 Google Cloud 實際使用計费；沒有承諾完全免費。

## 第三步：放入程式及環境變數

函式編輯器至少需要這五個檔案，放在同一層：

- main.py
- core.py
- faq.json
- legacy_messages.json
- requirements.txt

不要只覆蓋 main.py，否則會缺少檔案。容器方式則使用本包 Dockerfile，入口亦為 linebot。

| 名稱 | 值與用途 |
|---|---|
| LINE_CHANNEL_ACCESS_TOKEN | 您現有的 Channel access token，建議以 Secret Manager 掛入 |
| LINE_CHANNEL_SECRET | 您現有的 Channel secret，建議以 Secret Manager 掛入 |
| BOT_MODE | 第一輪設 `pilot`；確認通過才設 `live`；`off` 停用新問答、保留舊選單 |
| ADMIN_USER_IDS | 員工個人 LINE 的 user ID，多位以英文逗號隔開；第一次可先空白 |
| PILOT_USER_IDS | 測試者 user ID，多位以英文逗號隔開，可空白；管理員自動屬於測試者 |
| FIRESTORE_DATABASE | `(default)`，或您實際的資料庫名稱 |
| FIRESTORE_PREFIX | 預設 `lh_helpdesk_`；上線後勿任意更改，否則會讀不到既有人工狀態 |

先用 pilot 部署。一般民眾此時仍只有既有卡片與後台回覆；新問答僅對測試者開啟。

取得員工 ID：員工以自己的個人 LINE 私訊診所官方帳號，輸入 `/我的ID`。把收到的 U 開頭 33 字元 ID 填到 ADMIN_USER_IDS 後重新部署。**不能填 @開頭官方帳號 ID、LINE 暱稱、手機號碼。** 民眾查自己的 ID 不會取得管理員權限。

## 第四步：LINE 後台

1. LINE Developers → 既有 Messaging API Channel → Webhook URL 確認是此服務網址 → Verify，應成功。驗證只確認服務可接收，不等於 Firestore 已配置正確。
2. 啟用 Use webhook 與 Webhook redelivery。不要重新建立 Channel 或更換圖文選單。
3. LINE Official Account Manager → 設定 → 回應設定，確認聊天可用，員工能手動回覆，並能搭配 Webhook。
4. 檢查預設「每則訊息都回答」的自動回應，避免與本程式重複。三個固定關鍵字先保留。各帳號介面不同，以實際畫面確認回應組合。
5. 員工手機開啟 LINE 官方帳號 App 的聊天通知，安排服務時間內查看聊天室與待處理清單。

**這一版不會另外推播至員工群組，也不會自動把 LINE 後台的聊天室標成待處理。** 待處理清單是程式保存在 Firestore 的清單；員工需在自己的 LINE 向官方帳號查詢。若要專人群組主動通知，需要另行指定通知對象與實作。 **開啟自動轉專人後案件量會增加，請安排員工固定時段查看 `/客服 待處理`。**

## 第五步：人工處理方式

民眾：輸入問題 → 有核定答案就回答；對不上但有相近題就給按鈕；答不出來（或傳圖片、檔案）就自動登記待處理並給案件編號；民眾也可隨時輸入或點選「專人服務」。轉專人後之後可輸入「結束專人服務」自行恢復，或等 `PENDING_HOURS` 到期自動恢復。

員工：

1. 個人 LINE 向診所官方帳號傳 `/客服 待處理`。
2. 看到案件編號、初始問題及最新問題，每頁十筆；超過十筆使用回覆內提供的下一頁指令。
3. 到官方帳號後台相應聊天室人工回答。若無法對上案件，請民眾在原聊天室輸入「我的案件編號」提供編號，不要憑類似問題猜測對象。
4. 處理完畢後，從員工個人 LINE 傳 `/客服 結案 16字元案件編號`。
5. 收到「已結案」才表示這位民眾下次發問恢復機器人。只在後台手動回一句話**不會**自動結案。

結案不會自動發訊息給病患。案件的初始與最後問題文字在結案時刪除，保留狀態與結案人；完整對話仍在 LINE，需依診所原有管理方式處理。Firestore 每個待處理案件只保留最初、最近各 500 字，不存圖片及完整逐句病史。工作人員仍需閱讀 LINE 完整對話。

## 第六步：上線前實測（必做）

1. 測試者問「請問診所電話？」→ 一則電話回答＋請專人協助按鈕。
2. 問「有流感疫苗嗎」→ 相關問答按鈕；點其中一顆 → 收到該題答案。問「可以刷卡嗎」（題庫沒有、也無相近題）→ **自動收到待處理訊息與案件編號**；員工清單看得到這題。另開帳號輸入「謝謝」「你好」「好」→ 簡短回覆或不回應，**不開案件**。
3. 輸入「我兒子呼吸困難怎麼辦」→ 立即收到 119 訊息。
4. 輸入「專人服務」→ 待處理回覆＋案件編號；接著問「診所電話」→ 本程式不再回答；再輸入「孩子嘴唇發紫」→ **仍收到 119 訊息**。
5. 員工查待處理清單 → 可找到案件；一般使用者下結案指令應被拒絕。
6. 員工用官方帳號後台回答 → 民眾收到真人訊息。
7. 員工結案 → 民眾再問電話，恢復自動回答。另開一案測試民眾輸入「結束專人服務」也能恢復。
8. 驗證三個既有後台關鍵字、原醫師介紹、診所資訊卡片（時間為 24 小時制），以及輸入「立欣診所」出現診所資訊卡。
9. 傳貼圖 → 沒有回應；傳圖片 → 自動轉專人，收到待處理訊息。
10. 用未加入測試名單的帳號確認 pilot 不啟用新問答。
11. 確認當班員工看得到官方帳號聊天室、通知與待處理清單，最後才把 BOT_MODE 改 `live`。

## 回復與維護

- BOT_MODE 改 `off` 可停用新問答，員工管理指令仍可使用。原卡片會回復，不再受人工狀態阻擋，請通知當班人員。
- 如部署故障，Cloud Run 將流量切回原成功 revision；Firestore 案件仍保留。舊程式不識別新人工狀態，切回後務必人工追蹤未結案清單。
- **官網內容更新後**（門診時間、公告、衛教問答）：`python3 build_faq.py` 重新產生 faq.json，再部署。不確定要不要重產時跑 `python3 build_faq.py --check`，過期會 exit 1。預設從官網抓 knowledge.json 與 search.js；離線可用 `--kb`、`--search-js` 指定檔案。官網的緊急字詞規則若改了，build 會擋下，需先同步 `core.py`。
- **不要手改 faq.json**，下次重產會被覆蓋。答案內容要改請改官網；要多加一種問法請改 `aliases.json`（題目編號 → 問法），重跑 build。
- 不將「發燒」「用藥」等寬泛詞設為自動回答，避免個別病況被錯配。
- 測試：`pip install -r requirements.lock.txt` 後執行 `KB_PATH=…/knowledge.json SEARCH_JS=…/search.js python3 -m unittest`；不給這兩個路徑時，與官網比對的兩項會略過。
- 本機 tests 使用 mock 測試狀態邏輯與 Webhook，不代替真正 LINE／Firestore 整合測試。資料庫交易與 LINE 發訊無法組成單一原子交易，極少數「LINE 已收但網路回應遺失」會需人工檢查；LINE reply token 限制可避免同一 token 重複成功發送。
- 不需重跑修改圖文選單的 Colab；這次改動在 Cloud Run 後端與設定。
