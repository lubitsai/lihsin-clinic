### ③ ⚠️ 本批最重要的合規設計（中耳炎 × 非耳鼻喉專科）

中耳炎是與耳鼻喉科高度重疊的主題，而本院為小兒科與家庭醫學、**非耳鼻喉專科**（§4-5 不宣稱未具專科）。
處理方式：**專設一段「小兒科看得了中耳炎嗎？什麼時候要轉介耳鼻喉科」**，明寫

- **可做**：問診了解病程、以耳鏡檢查鼓膜、判斷是否為急性中耳炎、疼痛處理、依國內診治建議評估抗生素與安排回診追蹤；院內備耳鼻喉治療台（實際處置由醫師依病情評估）。
- **應轉介**：需聽力檢查、評估中耳通氣管等進一步處置、積液久不退或明顯影響聽力、短期反覆發作、鼓膜狀況需專科處理、出現危險徵象。

此定位同步寫進可見層、FAQ、隱藏區與 byline 四處，**不是只放在文末警語**。抗生素亦全程綁「由醫師評估、

### 工程教訓（三段式）

1. **現象**：中耳炎這種「別科也在看」的主題，很容易寫成一篇看起來很專業、卻實質暗示本院可以處理到底的文章。
   **根因**：衛教文章的完整性壓力（想把治療全講完）與診所的科別邊界會拉扯；只在文末警語補一句「非耳鼻喉專科」，
   讀者與 AI 都不會讀到那裡。
   **規則**：**跨科別主題開新頁時，把「本院可做什麼／什麼時候轉介」寫成獨立可見段落，並同步進 FAQ、
   隱藏區與 byline 四層**；判準是「家長讀完會不會以為這裡能做完所有處置」。
2. **現象**：新增一篇文章讓作者頁 description 從 80 字內變成 81 字，驗證器才抓到。
   **根因**：作者頁 desc 內含「N 篇衛教文章」的動態數字，篇數進位（9→10）會多一個字元，
   而六步整合的檢查清單只寫「篇數 +1」、沒寫「+1 後重量字數」。
   **規則**：**改到含數字的 meta 文案時（篇數、年份、價數），改完立即重算長度**；
   位數變化（個位進十位）是最容易破 80 字上限的時機。
3. **現象**：本批的 commit 落在本地 `main` 上，而 `git push` 推的是工作分支（仍停在上一批的位置），
   於是「推送成功」但遠端分支根本不含本批的兩篇新文章；交付說明已寫成「已推上分支」。
   **根因**：前一批合併後為了拉最新 main 而 `git checkout main`，接著直接開始新批次的產出，
   **沒有先切回工作分支**；push 指定了分支名所以不會報錯，錯誤完全靜默。
   **規則**：**每批開工第一個動作固定為 `git checkout -B <工作分支> origin/main` 並確認
   `git branch --show-current`；commit 前後各看一次分支名**。push 成功 ≠ 推到正確的分支，
   要以 `git log --oneline origin/<branch> -1` 確認遠端 tip 是本批的 commit。
   （本次是 stop hook 檢查 main 有未推送 commit 才發現——沒有那道檢查就會交付一個空的分支給院長。）
