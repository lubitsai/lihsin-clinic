## 〇、撤除是驗收條件，做法由院長裁示為「手動兩次」

**院長 2026-09-14 講了兩次**（第二次是在最終範圍確定之後再講一次），
接著第三次裁示定調了做法：**「可以在公告時間貼上，門診時間結束撤除，上系統修改兩次。」**

**＝院長接受手動操作兩次，不需要為了自動撤除把事情做大。**

**為什麼這條重要**：發布晚了，家長白跑一趟；
**撤除漏了，家長在診所正常收號的時間被告知「停止掛號」而不來**——
前者是不便，後者是把還會來的病人推走，而且會持續到有人發現為止。

> ⚠️ **這裡有一段被院長否決的顧慮，留著是為了不要再提第二次**：
> 我原本主張「撤除必須綁進開啟的動作裡、事後不能有要記得的事」，
> 理由是診所忙到要發停掛公告的那天正是最不可能記得回頭收拾的那天。
> **院長裁示上系統兩次可以接受 → 依 `02` R5 歸入「已評估並由院長裁定」，
> 不列待辦、不重啟討論。** 要重啟須院長重新裁示。
>
> 連帶影響：原本標為「最優先卡關」的「LINE 後台生效期間能不能指定單一天」
> **降級為加分項**——能設就少一次操作，不能設就手動關，兩者都可行。

**兩次操作分別做什麼，見 §一 操作卡。**

這兩診是全週僅有的兩位醫師同時看診的時段：

| 診次 | 蔡醫師 | 李醫師 | **撤除時刻** |
|---|---|---|---|
| **週日早診** | 08:00–11:00 | 08:00–11:30 | **11:30** |
| **週一晚診** | 18:30–21:00 | 18:30–21:30 | **21:30** |

**撤除時刻與上面那張表一致，不必另記**。理由：兩診都是**蔡醫師先下診**，

院長交付的圖方向正確。

**其餘五天每個診次都只有一位醫師** → 那位停掛就等於整個診次停掛，
用原本的早／午／晚三張即可，不需要醫師別版本。

## 二、為什麼自動化只能幫上一半

| 載體 | 發布 | 撤除 | 重要性 |
|---|---|---|---|
| **LINE 自動回應訊息** | ⚠️ **只能手動**（後台或手機 App） | ✅ **後台原生排程，分鐘級準時** | ⭐ 觸及 **6,653** 位好友 |
| **FB／IG 限時動態** | ✅ 可全自動 | ✅ 可自動（或 24h 自動消失） | 觸及較低 |

**這個組合有點反直覺**：最重要的那個載體（LINE）自動不了，
自動得了的那個（FB／IG）觸及較低。

⬜ **院長既然接受手動兩次，那 FB／IG 要不要做自動化就變成一個獨立問題**：
自動化能省的是「兩個平台各貼一次、各刪一次」＝四個動作變兩個按鈕，
代價是申請 Meta app、之後維護 token（會過期、會壞）。
**手機上手動發一則限動大概 30 秒。**
→ **待院長裁示：FB／IG 也照操作卡手動做，還是要我做自動化？**

## 三、LINE 自動回應訊息

### 3-1 ⚠️ 內容改不了，API 沒有這個東西

LINE Messaging API 管得到的是：推播／回覆訊息、圖文選單、用戶資料、受眾、
洞察報表、webhook 設定。**LINE 官方帳號後台「自動回應訊息」裡建立的那些項目，
沒有公開 API 可以新增、修改或個別開關**——只能在 LINE 官方帳號管理後台
（網頁版或手機 App）裡手動操作。

> ⚠️ **這一條我無法在本 session 自證**：`developers.line.biz` 與 firecrawl
> 都被本 session 的網路政策擋掉（egress proxy 403），讀不到官方 API 參考。
> 依通則 19，**標記為「依我的認知，未經一手文件查證」**——
> 院長或下一棒若在 LINE Developers 文件看到相反的東西，以文件為準。

### 3-2 唯一能全自動的路，代價不划算

技術上有一條路：**啟用 webhook，改用 Reply API 自己回**。那樣回什麼完全由程式決定，
停掛狀態只是一個旗標。但代價是：

- 要一台常駐伺服器（只有 `booking-system` 的 Docker 主機可用）。
- ⛔ **啟用 webhook 之後，回應的責任就整個從 LINE 後台轉到我們的程式**——
  現有的自動回應項目要全部用程式重做，漏掉哪一題，家長問那題就沒人回。
- ⛔ **伺服器掛掉＝官方帳號完全不回話**，比現在更糟。

**等於把「偶爾發一則停掛公告」換成「自建並維運一個 LINE 客服機器人」。
判斷：不建議。** 院長若仍要走這條，要當成獨立專案評估，不是本批的附帶工作。

### 3-3 後台的生效期間設定：能用就少一次動作（加分項，非必要）

LINE 自動回應訊息可以設定**生效日期、星期與時間區間**。若後台的生效期間
能指定到**單一天**，那院長開啟那則訊息時順手設好結束時刻，
**第二次上系統就不必再關 LINE**——時間一到它自己停止觸發，分鐘級準確。

**設定值＝§一 操作卡的撤除時刻表**（時間區間的起點用該診次的現場掛號受理時間：
早診 08:00／午診 14:30／晚診 18:00）。

> ⬜ **請院長在後台看一眼**（我看不到後台，無法代查）：
> **生效期間能不能指定到「單一天」**（設當天為起訖日，或設一個結束日）。
>
> - **能** → 第一次上系統就順手設好，第二次只要處理限動。
> - **不能**（只能設「每週幾」）→ ⚠️ **那就不要設生效期間**，
>   否則開著會每週的同一天同一時段重複觸發，安靜地錯下去。
>   照 §一 操作卡第二次上系統時手動關閉即可——**院長已裁示這樣可以接受**。
>
> 這一項**不卡任何事**，能用是賺到、不能用就照操作卡走。

⛔ **不要用「排一支提醒鬧鐘」來補**：提醒響的時候診所正在忙，
而且提醒本身不會關閉那則訊息，只是把「要記得」換個地方放而已。
要靠的是操作卡本身，不是額外的通知。

## 四、FB／IG 限時動態

### 4-1 可行性

| 項目 | 端點 | 費用 |
|---|---|---|
| FB 限時動態 | `POST /{page-id}/photo_stories` | 免費 |
| IG 限時動態 | `/{ig-user-id}/media`（`media_type=STORIES`）→ `/media_publish` | 免費 |
| FB 限動刪除 | `DELETE /{story-id}`（⚠️ 需實測） | — |
| IG 限動刪除 | `DELETE /{ig-media-id}` | — |

> **IG 限動可以刪**：Meta 的 Instagram Media 參考文件寫明
> 「Non-ad posts, stories, reels and entire carousel albums are supported for deletion」。
> **FB 限動的刪除端點我沒能親自查證**（egress 擋 `developers.facebook.com`），
> 依 Pages API 的一般規則推定可行，**列為實作時必須實測的項目，不要當成已知**。

**兩者都不能加文字說明**（IG 限動 API 不支援 caption），所以限動就是那張圖本身，
不需要文案。

### 4-2 院長需要準備的（一次性）

建一個 Meta app、綁 **立欣診所粉專**與 **IG 商業帳號**，取得 **Page access token**
（建議用 system user token，不會 60 天過期）。
權限：`pages_manage_posts`、`pages_read_engagement`、`instagram_basic`、
`instagram_content_publish`。

> `pages_manage_posts` **即使不發動態牆貼文也還是要**——FB 限時動態同樣需要粉專的
> CREATE_CONTENT 權限。
>
> 自家粉專、院長本人是 app 管理員的情況，通常 **Standard Access 就能發、不必送
> App Review**（Advanced Access 是給「管理別人的粉專」用的）。
> **這點要實測確認，不要當成已知。**

token 一律填進 **GitHub Secrets**，⛔ 不得寫進 `.mcp.json` 或任何 commit
（`CLAUDE.md` 架構約束）。

### 4-3 實作形狀與撤除

`internal/tools/publish_story.py` ＋ 一個 `workflow_dispatch` 的 GitHub Actions workflow：

```
選診次（早／午／晚）→ 同時發 FB 限動＋IG 限動 → 回報兩項各自的成功／失敗
```

- **圖從 `lhpedclinic.com.tw/images/social/…` 直出**——IG 要求公開 URL，本站本來就有。
  （這就是這批把圖放進 `images/` 而非 `internal/` 的原因。）
- **workflow 有手動按鈕**：院長在手機上就能自己按，不需要開 Claude session。
- **必備 `--dry-run`＋一次確認才真送**：發出去收不回。
- **Meta 會拒絕已經發過的素材**，所以發限動前要複製一份帶時間戳的檔名再上傳。

**撤除**用**對帳迴圈，不要用一次性定時器**：定期呼叫 `GET /{ig-user-id}/stories`
列出目前還活著的限動，找出我們發的那則、過了撤除時刻就刪。
好處是漏跑一輪下一輪會自己補，狀態存在 Meta 自己身上、不必 commit 狀態檔
（也就不會每次發公告都觸發一次 Netlify build）。

⚠️ **執行環境的誤差（依 §〇 這條是驗收條件，不能用「反正 24 小時會消失」帶過）**

GitHub Actions cron（repo 是 public，**分鐘數免費**）是 best-effort：
**尖峰常延遲 5～20 分鐘、偶爾整個跳過**。

**壓低誤差的作法**：掃描從撤除時刻前約 30 分鐘就開始、每 5 分鐘一次
（cron 最短間隔就是 5 分鐘）。每一輪各自延遲，但**只要有任何一輪在撤除時刻之後
執行到，就會刪**——多次機會把期望誤差壓到 **5 分鐘內，最差約 20 分鐘**。
提早開始掃不會提早刪：判斷式是 `now >= 撤除時刻`，不是「輪到就刪」。

**⛔ 但 GitHub 不保證一定會跑**，所以這是 best-effort、不是保證。
要**保證**的話只有一條路：把對帳排在我們自己控制的常駐主機上，
也就是 `booking-system` 的 Docker 主機（加一個獨立的 cron job，
**不動 booking-system 這個應用本身**）。MainPi 是第三方服務、不是我們的機器。

**判斷**：FB／IG 限動是「滑過去會看到」的東西，晚幾分鐘撤的傷害遠小於
LINE 自動回應（那是家長此刻正在問、直接回給他看的）。
所以**先用 GitHub Actions，等院長覺得誤差不可接受再搬到主機**——
但這是院長的取捨，不是我替他決定，已列為待院長項目。

⛔ **撤除時刻不得寫死在腳本裡**。門診時間會變（情境 B），寫死就會在改班表那天
悄悄失準。腳本要從 `index.html` 的 `SCHEDULE`／`EXCEPTIONS` 讀
（`sync_schedule.py` 已經在做同一件事，解析邏輯可以沿用），
**單日特例 `EXCEPTIONS` 也要吃**——颱風那天整日休診，撤除時刻當然不是平常的 12:00。
