## 一、操作卡：兩次上系統各做什麼

> **撤除時刻由 `index.html` 的 `SCHEDULE` 推導，不是手寫的。**
> 門診時間改了（情境 B）或當天有 `EXCEPTIONS` 單日特例（颱風、醫師進修），
> 這張表就要重算——**改班表的那一批要順手回來更新本表**。

### 撤除時刻表

| 停掛的診次 | 週一～五 | 週六 | 週日 |
|---|---|---|---|
| **早診** | 12:00 | 11:30 | 11:30 |
| **午診** | **17:55** ⚠️ | **18:00** | 無午診 |
| **晚診** | 21:30 | 無晚診 | 21:00 |

⚠️ **只有週一～五的午診要提早到 17:55**：那幾天午診看診到 18:00，
而**晚診的現場號也是 18:00 開始收**，兩者零空檔——撤晚了，家長會在晚診已經開始
收號的時候還看到「停止掛號」，以為整晚都不能來。
**週六不必提早**：週六沒有晚診，18:00 之後不會再收號，撤到 18:00 剛好。
早診與晚診後面都有兩個半小時以上的空檔，照實際結束時間撤即可。

| 順序 | 載體 | 動作 |

**LINE 排第一**：6,653 位好友，而且是家長「此刻正在問」的管道，最即時。

### 第二次上系統：撤除時（依上表的時刻）

| 順序 | 載體 | 動作 |
|---|---|---|
| 1 | **LINE 自動回應訊息** | **關閉那一則。⭐ 這是整張卡唯一「不做就會一直錯下去」的動作，沒有任何自動機制會代勞。** |
| 2 | **FB＋IG 限時動態** | **排程會自動撤**（見 §4-3），通常不必管。要立刻撤就跑 `action=teardown` 並勾 `force`。<br>（手動模式就是自己到兩個平台刪掉） |

> **⭐ 自動化之後，第二次上系統實質上只剩 LINE 那一件**——限動由排程撤、
> 而且就算排程整個漏掉，24 小時後也會自己消失。
> **LINE 那則是唯一不會自己消失的，不關就會一直錯下去。**
> 真的忙不過來只做得了一件事，做 LINE 那件。

### 另一種公告：醫師別停掛（院長 2026-09-14 補充）

除了整個診次停掛，還有一種是**只有一位醫師停掛、另一位仍開放**
（院長交付的圖：「蔡醫師停止掛號　僅開放李醫師掛號」）。

**⭐ 全週只有兩診會用到，已由 `index.html` 門診時間表程式化核對確認**——
這兩診是全週僅有的兩位醫師同時看診的時段：

| 診次 | 蔡醫師 | 李醫師 | **撤除時刻** |
|---|---|---|---|
| **週日早診** | 08:00–11:00 | 08:00–11:30 | **11:30** |
| **週一晚診** | 18:30–21:00 | 18:30–21:30 | **21:30** |

**撤除時刻與上面那張表一致，不必另記**。理由：兩診都是**蔡醫師先下診**，
但「蔡醫師停掛、僅開放李醫師」這個資訊在蔡醫師下診之後**仍然正確**
（家長要掛的本來就只剩李醫師），到李醫師也結束、整個診次收完才失效。
**所以撤除時刻用診次結束時間，不是停掛那位醫師的下診時間。**

⚠️ **兩診都是蔡醫師先下診**，所以「蔡醫師先額滿」正是會發生的方向，
院長交付的圖方向正確。

**其餘五天每個診次都只有一位醫師** → 那位停掛就等於整個診次停掛，
用原本的早／午／晚三張即可，不需要醫師別版本。

## 二、為什麼自動化只能幫上一半

| 載體 | 發布 | 撤除 | 重要性 |
|---|---|---|---|
| **LINE 自動回應訊息** | ⚠️ **只能手動**（後台或手機 App） | ✅ **後台原生排程，分鐘級準時** | ⭐ 觸及 **6,653** 位好友 |
| **FB／IG 限時動態** | ✅ 可全自動 | ✅ 可自動（或 24h 自動消失） | 觸及較低 |

**這個組合有點反直覺**：最重要的那個載體（LINE）自動不了，
自動得了的那個（FB／IG）觸及較低。

**✅ 院長 2026-09-14 裁示「FB／IG 做自動化」→ 已實作完成（§4-3）。**
發布變成一個按鈕、撤除由排程自動做；**代價是要維護 Meta token**（會過期、會壞），
token 壞掉時 workflow 會紅燈，屆時照 §4-2 重新取一次填進 Secrets 即可。
**手動路徑仍然可用、沒有被移除**——Secrets 沒設好或 Meta 出狀況時，
照 §一 操作卡自己到兩個平台貼圖刪圖，效果完全一樣。

## 三、LINE 自動回應訊息

### 3-1 ⚠️ 內容改不了，API 沒有這個東西

LINE Messaging API 管得到的是：推播／回覆訊息、圖文選單、用戶資料、受眾、
洞察報表、webhook 設定。**LINE 官方帳號後台「自動回應訊息」裡建立的那些項目，
沒有公開 API 可以新增、修改或個別開關**——只能在 LINE 官方帳號管理後台
（網頁版或手機 App）裡手動操作。

> ⚠️ **這一條我無法在本 session 自證**：`developers.line.biz` 與 firecrawl
> 都被本 session 的網路政策擋掉（egress proxy 403），讀不到官方 API 參考。
> 依通則 19，**標記為「依我的認知，未經一手文件查證」**——
> 院長或下一棒若在 LINE Developers 文件看到相反的東西，以文件為準。

### 3-2 唯一能全自動的路，代價不划算

技術上有一條路：**啟用 webhook，改用 Reply API 自己回**。那樣回什麼完全由程式決定，
停掛狀態只是一個旗標。但代價是：

- 要一台常駐伺服器（只有 `booking-system` 的 Docker 主機可用）。
- ⛔ **啟用 webhook 之後，回應的責任就整個從 LINE 後台轉到我們的程式**——
  現有的自動回應項目要全部用程式重做，漏掉哪一題，家長問那題就沒人回。
- ⛔ **伺服器掛掉＝官方帳號完全不回話**，比現在更糟。

**等於把「偶爾發一則停掛公告」換成「自建並維運一個 LINE 客服機器人」。
判斷：不建議。** 院長若仍要走這條，要當成獨立專案評估，不是本批的附帶工作。

### 3-3 ⛔ 生效期間不能指定單一天——已驗證，不要設它

**院長 2026-09-14 在後台實查回報：生效期間不能指定到單一天。**
原本設想的「開啟時順手設好結束時刻、第二次上系統就不必再關 LINE」**不成立**。

⛔ **所以不要設生效期間**。後台只能設「每週幾」，設下去的後果是
**每週的同一天同一時段自動重複觸發**——例如為了週一晚診設「每週一 18:30–21:30」，
那**每一個**週一晚上都會對家長說「停止掛號」，不管那天有沒有停掛。
**這是安靜地錯下去，沒有任何人會發現。**

⚠️ **這個陷阱在本院特別容易踩**：醫師別停掛只發生在**週一晚診**與**週日早診**，
兩個都是固定星期——看起來「剛好可以用星期排程做掉」，但**停掛只發生在忙的那幾天、
不是每個週一週日**。星期固定 ≠ 每週都要發。

✅ **正確作法＝照 §一 操作卡，第二次上系統手動關閉**。
院長已裁示「上系統修改兩次」可以接受，本來就是這樣設計的。

## 四、FB／IG 限時動態

### 4-1 可行性

| 項目 | 端點 | 費用 |
|---|---|---|
| FB 限時動態 | `POST /{page-id}/photo_stories` | 免費 |
| IG 限時動態 | `/{ig-user-id}/media`（`media_type=STORIES`）→ `/media_publish` | 免費 |
| FB 限動刪除 | `DELETE /{story-id}`（⚠️ 需實測） | — |
| IG 限動刪除 | `DELETE /{ig-media-id}` | — |

> **IG 限動可以刪**：Meta 的 Instagram Media 參考文件寫明
> 「Non-ad posts, stories, reels and entire carousel albums are supported for deletion」。
> **FB 限動的刪除端點我沒能親自查證**（egress 擋 `developers.facebook.com`），
> 依 Pages API 的一般規則推定可行，**列為實作時必須實測的項目，不要當成已知**。

**兩者都不能加文字說明**（IG 限動 API 不支援 caption），所以限動就是那張圖本身，
不需要文案。

### 4-2 院長需要準備的（一次性）

建一個 Meta app、綁 **立欣診所粉專**與 **IG 商業帳號**，取得 **Page access token**
（建議用 system user token，不會 60 天過期）。
權限：`pages_manage_posts`、`pages_read_engagement`、`instagram_basic`、
`instagram_content_publish`。

> `pages_manage_posts` **即使不發動態牆貼文也還是要**——FB 限時動態同樣需要粉專的
> CREATE_CONTENT 權限。
>
> 自家粉專、院長本人是 app 管理員的情況，通常 **Standard Access 就能發、不必送
> App Review**（Advanced Access 是給「管理別人的粉專」用的）。

#### ⭐ 撤除時刻是算出來的，不是寫死的

#### 排程與誤差

`cron: */10 3,4,9,10,13,14 * * *`（UTC）——涵蓋三個撤除時段前後各一小時、
每 10 分鐘掃一次。判斷式是 `now >= 撤除時刻`，**提早開始掃不會提早刪**。

⚠️ GitHub 排程是 best-effort（尖峰常延遲 5～20 分鐘、偶爾整個跳過），
所以這是**盡力而為、不是保證**。靠掃描密度與「漏跑下一輪會自己補」吃掉誤差。
**限動 24 小時本來就會自己消失，所以最壞情況也只是晚幾分鐘撤**——
真正不能漏的是 LINE 那則，而那本來就是手動的（§一）。

#### 幾個刻意的防呆

- **發布前先 HEAD 一次圖片 URL**：IG 要求公開 URL，圖掉了的話 IG 只會回一個難解的錯誤。
  （本機 egress 擋本站網域 → 只印警告不擋；在 CI 上才是真檢查。）
- **圖片 URL 帶時間戳查詢字串**（`?v=<unix>`）：Netlify 照樣回同一個檔，
  但對 Meta 而言是不同 URL，避開「同一素材不得重複發布」的可能判定。
- **FB 走兩段式**（先 `POST /{page-id}/photos` 拿 `photo_id`、再 `POST /{page-id}/photo_stories`）：
  每次都重新上傳＝每次都是新的 `photo_id`，同樣避開素材重複使用的限制。
- **已有在線上的限動時拒絕再發**（要蓋掉得加 `--force`），避免重複貼。
- **過了撤除時刻就拒絕發布**，避免發一則立刻就要撤的公告。
- **醫師別只允許週日與週一**，其餘日子直接擋下並提示改用整診停掛（已實測）。
- **FB 限動刪除失敗只警告、不讓整批失敗**——該端點未經一手文件查證（§4-1），
  而且刪不掉不是災難，24 小時會自己過期。
- **狀態檔回寫失敗會讓 workflow 紅燈**並印出原因：狀態掉了＝下一輪撤除掃描
  找不到 media id，這個必須讓人看見。
