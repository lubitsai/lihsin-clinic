## 一、結論先講：兩個載體，自動化程度完全不同

| 載體 | 發布 | 撤除 | 重要性 |
|---|---|---|---|
| **LINE 自動回應訊息** | ⚠️ **只能手動**（後台或手機 App） | ✅ **後台原生排程，分鐘級準時** | ⭐ 觸及 **6,653** 位好友 |
| **FB／IG 限時動態** | ✅ 可全自動 | ✅ 可自動（或 24h 自動消失） | 觸及較低 |

**這個組合有點反直覺，要講清楚**：最重要的那個載體（LINE）自動不了，
自動得了的那個（FB／IG）觸及較低。所以請院長先評估
「為了 FB／IG 兩則限動去申請 Meta app、維護 token」值不值得——
**手機上手動發一則限動大概 30 秒**，自動化省下的是「兩個平台各做一次」和
「不用記得回來刪」。這是取捨題，不是技術題。

## 二、LINE 自動回應訊息

### 2-1 ⚠️ 內容改不了，API 沒有這個東西

LINE Messaging API 管得到的是：推播／回覆訊息、圖文選單、用戶資料、受眾、
洞察報表、webhook 設定。**LINE 官方帳號後台「自動回應訊息」裡建立的那些項目，
沒有公開 API 可以新增、修改或個別開關**——只能在 LINE 官方帳號管理後台
（網頁版或手機 App）裡手動操作。

> ⚠️ **這一條我無法在本 session 自證**：`developers.line.biz` 與 firecrawl
> 都被本 session 的網路政策擋掉（egress proxy 403），讀不到官方 API 參考。
> 依通則 19，**標記為「依我的認知，未經一手文件查證」**——
> 院長或下一棒若在 LINE Developers 文件看到相反的東西，以文件為準。

### 2-2 唯一能全自動的路，代價不划算

技術上有一條路：**啟用 webhook，改用 Reply API 自己回**。那樣回什麼完全由程式決定，
停掛狀態只是一個旗標。但代價是：

- 要一台常駐伺服器（只有 `booking-system` 的 Docker 主機可用）。
- ⛔ **啟用 webhook 之後，回應的責任就整個從 LINE 後台轉到我們的程式**——
  現有的自動回應項目要全部用程式重做，漏掉哪一題，家長問那題就沒人回。
- ⛔ **伺服器掛掉＝官方帳號完全不回話**，比現在更糟。

**等於把「偶爾發一則停掛公告」換成「自建並維運一個 LINE 客服機器人」。
判斷：不建議。** 院長若仍要走這條，要當成獨立專案評估，不是本批的附帶工作。

### 2-3 ✅ 但「撤除」後台原生就能做，而且比我做的還準

LINE 自動回應訊息可以設定**生效日期、星期與時間區間**。所以院長建立那則停掛訊息時，
**把日期設成當天、時間區間設成該診次**，時間一到它就自己不再觸發——
**不需要任何撤除動作，也不需要我排 cron，而且是分鐘級準確**
（我用 GitHub cron 反而會晚 5～20 分鐘，見 §3-3）。

**建議的常備作法**：預先建好三則、平常關閉，要用時只要開啟並把日期改成今天。

| 停掛的診次 | 時間區間設定 |
|---|---|
| 早診 | 08:00–12:00（週六日 08:00–11:30） |
| 午診 | 14:30–**17:55** ⚠️ |
| 晚診 | 18:00–21:30（週日 18:00–21:00） |

⚠️ **午診那格刻意在 17:55 結束**：午診看診到 18:00，但**晚診的現場號也是 18:00 開始收**，
兩者零空檔。若設到 18:00，家長會在晚診已經開始收號時還收到「停止掛號」，
以為整晚都不能來。早診與晚診後面都有兩個半小時以上的空檔，照實際結束時間設即可。

> ⬜ **請院長在後台實際確認兩件事**（我看不到後台，無法代查）：
> ① 日期能不能指定「單一天」——如果只能設「每週幾」，那開著就會每天觸發，
>   用完仍需手動關閉，自動撤除就不成立。
> ② 開啟／關閉一則自動回應訊息，在手機 App 上是幾個動作。
>   如果超過五、六下，值得改成「三則各自設好、只切換啟用」的作法。

## 三、FB／IG 限時動態

### 3-1 可行性

| 項目 | 端點 | 費用 |
|---|---|---|
| FB 限時動態 | `POST /{page-id}/photo_stories` | 免費 |
| IG 限時動態 | `/{ig-user-id}/media`（`media_type=STORIES`）→ `/media_publish` | 免費 |
| FB 限動刪除 | `DELETE /{story-id}`（⚠️ 需實測） | — |
| IG 限動刪除 | `DELETE /{ig-media-id}` | — |

> **IG 限動可以刪**：Meta 的 Instagram Media 參考文件寫明
> 「Non-ad posts, stories, reels and entire carousel albums are supported for deletion」。
> **FB 限動的刪除端點我沒能親自查證**（egress 擋 `developers.facebook.com`），
> 依 Pages API 的一般規則推定可行，**列為實作時必須實測的項目，不要當成已知**。

**兩者都不能加文字說明**（IG 限動 API 不支援 caption），所以限動就是那張圖本身，
不需要文案。

### 3-2 院長需要準備的（一次性）

建一個 Meta app、綁 **立欣診所粉專**與 **IG 商業帳號**，取得 **Page access token**
（建議用 system user token，不會 60 天過期）。
權限：`pages_manage_posts`、`pages_read_engagement`、`instagram_basic`、
`instagram_content_publish`。

> `pages_manage_posts` **即使不發動態牆貼文也還是要**——FB 限時動態同樣需要粉專的
> CREATE_CONTENT 權限。
>
> 自家粉專、院長本人是 app 管理員的情況，通常 **Standard Access 就能發、不必送
> App Review**（Advanced Access 是給「管理別人的粉專」用的）。
> **這點要實測確認，不要當成已知。**

token 一律填進 **GitHub Secrets**，⛔ 不得寫進 `.mcp.json` 或任何 commit
（`CLAUDE.md` 架構約束）。

### 3-3 實作形狀與撤除

`internal/tools/publish_story.py` ＋ 一個 `workflow_dispatch` 的 GitHub Actions workflow：

```
選診次（早／午／晚）→ 同時發 FB 限動＋IG 限動 → 回報兩項各自的成功／失敗
```

- **圖從 `lhpedclinic.com.tw/images/social/…` 直出**——IG 要求公開 URL，本站本來就有。
  （這就是這批把圖放進 `images/` 而非 `internal/` 的原因。）
- **workflow 有手動按鈕**：院長在手機上就能自己按，不需要開 Claude session。
- **必備 `--dry-run`＋一次確認才真送**：發出去收不回。
- **Meta 會拒絕已經發過的素材**，所以發限動前要複製一份帶時間戳的檔名再上傳。

**撤除**用**對帳迴圈，不要用一次性定時器**：定期呼叫 `GET /{ig-user-id}/stories`
列出目前還活著的限動，找出我們發的那則、過了撤除時刻就刪。
好處是漏跑一輪下一輪會自己補，狀態存在 Meta 自己身上、不必 commit 狀態檔
（也就不會每次發公告都觸發一次 Netlify build）。

⚠️ **執行環境的誤差**：GitHub Actions cron（repo 是 public，**分鐘數免費**）
是 best-effort，**尖峰常延遲 5～20 分鐘、偶爾整個跳過**。
限動 24 小時本來就會自己消失，所以這個誤差在 FB／IG 這邊是可接受的——
**真正需要準時的 LINE 那條，剛好是用後台原生排程、不受這個誤差影響**（§2-3）。

⛔ **撤除時刻不得寫死在腳本裡**。門診時間會變（情境 B），寫死就會在改班表那天
悄悄失準。腳本要從 `index.html` 的 `SCHEDULE`／`EXCEPTIONS` 讀
（`sync_schedule.py` 已經在做同一件事，解析邏輯可以沿用），
**單日特例 `EXCEPTIONS` 也要吃**——颱風那天整日休診，撤除時刻當然不是平常的 12:00。

## 四、素材（本批已產出，可立即使用）

院長對話上傳的三張 1254×1254 公告圖（早診／午診／晚診各一款，**無日期、可重複使用**），
入庫於 `images/social/`，並各產一份 9:16 限動版：

| 檔案 | 尺寸 | 用途 |
|---|---|---|
| `registration-closed-morning.jpg` | 1254² | 產限動版的來源；**若 LINE 自動回應改回圖片**（§2-4）也用這張 |
| `registration-closed-morning-story.jpg` | 1080×1920 | **FB／IG 限動（早診）** |
| `registration-closed-afternoon.jpg` | 1254² | 同上（午診） |
| `registration-closed-afternoon-story.jpg` | 1080×1920 | **FB／IG 限動（午診）** |
| `registration-closed-evening.jpg` | 1254² | 同上（晚診） |
| `registration-closed-evening-story.jpg` | 1080×1920 | **FB／IG 限動（晚診）** |

**為什麼要另產限動版**：限動畫布是 9:16，方形圖直接上傳會被上下補黑邊或左右裁掉字。
工具 `internal/tools/make_story_image.py` 把方形圖置中放在 1080×1920 上，
上下留白取圖**四個角落的平均色**往接縫漸層——晴天版得到淺藍、夕陽版得到橘、
夜晚版得到深藍，三款各自對得上，不必手動配色。

> **踩過的兩個雷（已寫進工具 docstring，不要再試一次）**：
> ① `--bg blur`（整張放大模糊填滿）取到的是圖的**中段米色文字框**，夜晚版會糊成土色、
> 和深藍天空對不上。
> ② `--bg edge`（邊緣像素往外拉伸）會把**上緣的綠色布條**和**下緣的米色資訊列**
> 拉成看得出字影的直向拖影。
> → 預設 `--bg solid` 是唯一在這三款上都乾淨的作法。

**版位安全區已確認**：公告圖落在 y 420–1500，IG 頂部頭像（約 250px）與底部回覆列
（約 250px）都蓋不到。

⚠️ **這三組刻意放 `images/social/`，不放 `images/notice/`**：
`images/notice/` 是官網 `#clinic-notice` 用的**當期**公告圖，受 SOP §一.6
「公告下架後一併刪檔、只留當期那一組」的清理規則管。這三組是**常駐重複使用的社群模板**，
放進 `notice/` 會在下一次清理時被誤刪。
**也不要移進 `internal/pending-images/`**——該目錄的 README 載明
「9/16 換完請刪除本目錄整個資料夾」，放進去會被流感疫苗那批的清理動作一併刪掉。

⚠️ **這三組不要掛上官網公告區**：圖上寫「本日」但沒有日期，官網是持續存在的頁面，
掛上去等於每天都在說「本日停掛」。官網的當日公告仍走 `clinic-schedule` 既有流程
（帶日期的公告圖 ＋ `data-expires`）。
**而且院長已明確裁示官網不在發布範圍內。**
