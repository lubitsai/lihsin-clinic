## 4. ⭐ 教訓（三段式）

- **現象**：10-06o 盤點宣告「health/ 單圖文章全數已符合」，同一條裁示的屬性要求卻在 60 頁未落實，靠 Lighthouse 13.4 s 才發現。**根因**：盤點只驗了裁示的一半（位置），另一半（`loading`／`fetchpriority`）沒有任何檢查會亮。**規則**：裁示含多個可檢查條件時，盤點要逐條程式化驗證，每一條各自出一個數字；只驗一條不得寫「全數符合」。

## 5. 勘誤（同日，run #15）——實驗室數據單次變異很大，13.4 s 不能當常態

`health-check-live` run **#15**（`main` `cc9b248`，此時 PR #361 **尚未合併**、線上頁面與 run #14 完全相同）同頁重測：

| 頁面 | run #14 | run #15 |
|---|---|---|
| 首頁 手機 | 61 分／TBT 3,630 ms／CLS 0.113 | 82 分／TBT 600 ms／CLS 0.061 |
| `shingles-vaccine` 手機 LCP | **13.4 s** | **3.2 s** |
| `growth` 手機 CLS | 0.056 | 0.148 |

- **P1 的嚴重度要下修**：13.4 s 大半是 runner 單次變異。修法本身仍成立——run #15 確認該頁 LCP 元素**就是**那張 lazy 的衛教圖（`shingles-vaccine-infographic-768.webp`），3.2 s 仍高於 2.5 s 門檻；合併後以多次量測確認改善，不以單次數字下結論。
- **首頁 CLS 0.113 不成立為問題**：run #15 為 0.061（主要位移 `ul.grid` 0.055、`#fab-group` 0.007），field 為 0 → 結案，不追。
- **新觀察（單次、不動作）**：桌機首頁 CLS 0.091（`nav#navbar` 桌機選單）、`growth` 手機 CLS 0.148（`#addAssessCard`）。兩者都只有一次樣本，下次 run 若仍 > 0.1 再查。
- **⭐ 教訓**：**現象**＝同一頁、相隔 15 分鐘、程式碼未變，LCP 13.4 s → 3.2 s。**根因**：GitHub runner 的 Lighthouse 是模擬節流，單次變異可以差到 4 倍。**規則**：實驗室數據要嘛連跑 ≥ 3 次取中位數，要嘛以 field（CrUX）為準；單次 run 只能當「去看」的訊號，不能寫成嚴重度。

### ⭐ 教訓（三段式）
- **現象**：合併後連 3 次 CLS 0.17，判為回退並開了回退 PR；A/B 才發現舊版也會出現 0.17。**根因**：拿「改動後的 3 次」和「改動前的 2 次」比，兩組不同時間、不同網路狀況，前後比較會把偶發事件算到改動頭上。**規則**：判定一個改動「造成回退」前，要在**同一時段、同一環境**對兩版做 A/B（Deploy Preview vs 正式站，各 ≥3 次）；只有前後比較時，只能寫「疑似」、不能據以回退。
