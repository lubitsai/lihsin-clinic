## 三、政策決定紀錄（2026-08-01 院長裁示）

### D7：額度算「帳號」還是「病人」？

- **官網現行（BookNow）＝帳號**：一個家長帳號最多 2 筆，不管是幫哪個孩子約。
- **自建系統目前＝病人**：每個孩子各自 2 筆，家長有 3 個孩子就能有 6 筆。

兩者差異很大。考量點：

- 算**病人**較符合臨床公平性（每個孩子的看診機會相同），且櫃檯代約時本來就沒有「帳號」可歸屬（電話代約的民眾沒有註冊帳號）。
- 算**帳號**與現行公告一致，但多寶家庭會覺得額度不夠用，且無法涵蓋櫃檯代約。

**院長裁示：採帳號制**（與官網公告一致）。實作說明：LINE 登入者以 LINE 帳號為單位、未登入者以通過驗證的手機號碼為單位；櫃檯代約沒有帳號，不占任何帳號額度也不受此限（櫃檯本就可覆寫）。多寶家庭的額度壓力由 D9 家庭代表預約紓解。

### D8：超額時「自動取消第 3 筆」還是「擋下不讓約」？

- 官網現行是**事後自動取消**且不另行通知——民眾可能以為約好了，到現場才發現被取消。
- 自建系統是**當下就擋下並說明原因**，民眾立刻知道要先取消哪一筆。

**院長裁示：維持「當下擋下」**。系統不會自動取消民眾既有的預約；超額時明確告知需先取消或完成既有預約。切換上線時，官網公告該句需同步改寫（可見文字，需院長逐字核可）。

### D3：報到逾時採「標記」而非「自動取消」

公告寫的是「逾時該筆預約即取消，需重新抽現場號」。系統實作為：
櫃檯總覽在時段開始 N 分鐘（`booking.checkin_grace_minutes`，預設 10）後，
把該筆標成紅框＋「報到逾時」，每 30 秒重算，**但不動狀態**。

理由：櫃檯忙碌時報到本來就會延後，家長也可能人已在現場等著；
系統若自動取消，會出現「人在櫃檯前、預約卻被系統取消」的情況，比逾時本身更難處理。
公告的效果（逾時要重抽現場號）由櫃檯按既有按鈕完成，且與 Q13「逾時但當天仍有來看診＝不記未到」
一致——那項判斷本來就只有櫃檯知道。

**院長 2026-08-05 裁示：維持現狀。** 公告文字一樣寫「即取消」，實際執行由櫃檯處理、保留判斷空間。
＝對家長講的效果一致，櫃檯則能依現場狀況決定（人已在等就照常報到、逾時仍有來看診不記未到）。
> 日後若有人看到「公告說即取消、系統卻沒取消」而想「修正」，這是刻意的，非待辦。
> 真要改為自動取消，需要一支排程（每分鐘掃描）＋決定自動取消是否計入未到次數，屬另案。

### D11：取消截止一律以「診次」為單位（院長 2026-08-06 確認）

**結論：規則是「當診次開始後即停止取消當診次的預約」，不看個別時段的時間。**
＝ D4 的規則不變，這裡是把它明確釘死，並記下一次走錯的路。

#### 走過的岔路：曾加過「時段開始就擋」，已移除

發現的現象是真的：判斷診次要靠當日班表，一旦某筆預約的時間落在所有班表區間之外，
系統只能依時間粗分回最接近的診次，於是「時段已經開始、診次卻還沒開診」就成立了。

- 早診原本 08:00 開始，之後改成 09:00（**官網門診時間異動後跑 `sync_schedule.py` 就會這樣改**），
  已成立的 08:00 預約落在區間外 → 粗分回早診 → 早診 09:00 才開診 → 08:30 家長仍取消得掉。
- 後台直接改週班表（`adminUpsertTemplate` / `adminDeleteTemplate`）同理。
- （院長已確認**不會有櫃檯手動加開時段**，`appointment_slots.source = MANUAL` 那條路不列入考量。）

當時據此加了一道「`now >= 該筆預約的時段時間` 就擋」的底線。**這是錯的方向**：那個 08:30，
診所根本還沒開始看診，這筆預約的時間也已經不存在於班表上——擋住家長取消，只會讓他既走不掉、
又在 09:00 之後被記一次未到。**放行才是對的**，家長取消掉反而讓診所少一個空號。

因此該判斷已移除，`MSG.slotStarted`、`/rules` 對應條目、`08` 表 5-7c 一併撤掉。
> 日後若有人看到「時段都過了還能取消」而想「補一道防線」，這是刻意的，非待辦。

#### 現行判斷順序

1. 未來日期 → 一律可取消
2. 過去日期 → 擋
3. 該筆預約所屬**診次**已開診 → 擋（`MSG.cutoffPassed`）
4. 查不到該診次（該診別當日整個不在班表上）→ 退回 `booking.cancel_cutoff_minutes`（120 分鐘）備援

櫃檯不受此限（與開診限制一致，等同現場處理）。

回歸測試：`tests/announced-rules.test.ts` →「取消截止一律以診次為單位」。
釘住班表改動後那個容易被誤修的情形：08:30（時段已過、診次未開）**可以**取消，
09:30（診次已開）擋下。

> **真正該處理的不是取消規則，是那筆孤兒預約本身**——班表改掉後預約還留在診所不看診的
> 時間，見 §五第 3 點。

### D12：改常態班表比照單日例外（院長 2026-08-06 裁示 (a)）

查 D11 時發現的：單日例外（停診／代診／特殊時間）建立前會跑 `findAffectedAppointments`，
把落在新班表外的預約攔下來要求處理；但**改常態班表的兩條路都沒有這道檢查**——

- 後台「排班 → 固定週班表」改／刪一列
- **官網門診時間異動後跑同步**（`applySchedule`：會改時間，也會刪掉整列）

後果是預約留在診所已經不看診的時間，系統不通知、櫃檯總覽也不提示，家長仍會照原時間到院。
D11 已確認不能用取消規則去繞（擋住家長取消只會讓他被記未到），要從源頭解決。

**現在兩條路都比照單日例外：**

| | 檢查範圍 | 擋下時 | 確認後 |
|---|---|---|---|
| 後台改／刪週班表 | 今天起所有有效預約 | **班表完全不動**，畫面列出受影響名單（日期／時間／姓名／電話／編號），可逐筆改期 | 勾選批次取消＋填原因 → 取消與班表變更同一交易，並排入通知 |
| 官網同步 | 同上 | **整批不寫入**，命令列印出名單並以 exit code 2 結束 | `--cancel-affected` 再跑一次 |

實作重點：

- **先算再寫**。`planSchedule()` 由官網資料推出「應有的週班表與單日例外」，純計算不碰資料庫；
  檢查通過才進入寫入階段。原本是邊算邊寫，沒有可以喊停的時點。
- **模擬用的是同一套邏輯**。`blocksFromTemplates()` 與 `isSlotCovered()` 由實際班表計算與
  受影響模擬共用（`applyExceptions` 本來就是這樣），模擬結果才會跟真的算出來一樣。
- **官網同步的例外也要一起模擬**。同步會把自己上次建的例外整批換掉，檢查時得用換完的那一組，
  否則會拿舊例外去對新班表；櫃檯自己建的例外不在替換範圍，照樣沿用（`exceptionsFor` 回呼）。
- **只檢查官網有寫到的星期**。官網沒提到的星期，既有班表列原封不動，也不列入受影響判斷。
- 同步的寫入與取消包在同一個交易（`scripts/sync-schedule.ts`），中途失敗整批回滾。

回歸測試：`tests/schedule-change-guard.test.ts`（8 項，涵蓋兩條路的擋下／確認後生效／
時間縮短但預約仍在區間內時直接生效／整日休診）。已確認拿掉兩處判斷後會紅 4 項。
