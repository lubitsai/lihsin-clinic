# 06｜本機啟動、正式部署、備份與還原

## 一、本機開發啟動

需求：Node.js 22+、PostgreSQL 16+（本機或 Docker）。

```bash
cd booking-system
npm install

# 準備資料庫（例：docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=dev postgres:16-alpine）
cp .env.example .env        # 填入本機 DATABASE_URL 與隨機密鑰
npx prisma migrate deploy   # 建立資料表
npm run db:seed             # 醫師/門診/班表/測試帳號（admin、counter1）
npm run dev                 # http://localhost:3000
```

- 前台：`http://localhost:3000`；後台：`http://localhost:3000/admin`
- 開發模式下 OTP 簡訊印在終端機（`SMS_PROVIDER=console`），驗證碼欄會自動帶入。
- 測試：`npm test`（需 `lihsin_booking_test` 資料庫，見 `tests/global-setup.ts`）。

## 二、正式部署（Docker Compose）

### 2-0 主機：Google Cloud Compute Engine（院長 2026-08-06 改定）

> 原訂 DigitalOcean Droplet（Singapore），2026-08-06 改為 Google Cloud。
> **最大的差別是資料可以放在台灣**：GCP 有彰化機房（`asia-east1`），
> DO 沒有台灣機房才必須放新加坡。個資告知文字維持現行（院長 2026-08-05 裁示），
> 但「資料存放於新加坡」這個前提已不成立，屆時如要對外說明可據實寫台灣。

**用 Compute Engine 的虛擬機，不要用 Cloud Run。** 這套系統是 Docker Compose 起
app＋PostgreSQL＋每日備份＋提醒排程四個服務，VM 可以原封不動照 §2-1 部署；改用 Cloud Run
要拆成 Cloud SQL＋Cloud Scheduler＋Secret Manager，是另一套架構，也更綁死在 GCP 上
（違反「程式碼與資料庫必須可移轉」）。日後真要換雲，VM 這條路搬走只是重跑一次 §2-1。

| 項目 | 選擇 | 說明 |
|---|---|---|
| 專案 | 用**診所自己的 Google 帳號**開新專案，例如 `lihsin-booking` | 專案擁有者必須是診所控制的帳號，不要掛在個人或廠商帳號下 |
| 產品 | Compute Engine → VM 執行個體 | |
| 區域 | **`asia-east1`（彰化，台灣）**，可用區 `asia-east1-b` | 資料留在台灣、延遲也最低。**不要選 `asia-east2`**，那是香港 |
| 機型 | **`e2-medium`**（2 vCPU / 4GB） | 見下方〈實測資源用量〉。`e2-small`（2GB）可行但必須加 swap；GCP 沒有「1 vCPU」的 e2 機型 |
| 開機磁碟 | Ubuntu 24.04 LTS、**50GB**、`pd-balanced` | 預設只有 10GB，一定要改大 |
| 外部 IP | 在「網路介面」把 IP 改為**保留靜態 IP** | 用預設的臨時 IP，VM 一停一開就換 IP，DNS 會失效 |
| 登入 | `gcloud compute ssh`（OS Login） | GCE 的 Ubuntu 映像預設就關閉密碼登入 |
| 快照 | 幫開機磁碟掛**快照排程**（每日、保留 14 天） | 與 §三 的 pg_dump 互補：快照救「整台壞掉」，dump 救「資料被誤刪」 |
| 帳單 | 到「帳單 → 預算與快訊」設一個**預算警示** | GCP 是用多少算多少，跟 DO 的固定月費不同；設個上限才不會被對外流量嚇到 |

> **沒有免費額度可用**：GCP 的 `e2-micro` 永久免費方案只限美國區域，`asia-east1` 不適用。

#### 實測資源用量（2026-08-06 於本專案實際量測）

| 項目 | 峰值 RSS | 說明 |
|---|---|---|
| **`next build`** | **約 1,060 MB** | 所有 node 程序合計。**這是決定機器大小的那一項** |
| Next.js 執行期（standalone） | 130 MB（峰值 151 MB） | 連續開過首頁／預約／規則／我的預約／後台登入之後 |
| PostgreSQL 16 | 約 141 MB | 11 個程序合計 |

執行期整套（app＋db＋備份＋提醒排程＋Docker＋作業系統）約 **500–700 MB**，
所以 **2GB 跑起來很夠**；卡住的是**建置**：

- `docker compose up -d --build` 會在容器內跑 `next build`，峰值約 1GB；
- 重新部署時 PostgreSQL 通常已經在跑，再吃掉約 140MB；
- 2GB 機器上 Node 的預設 heap 上限也會跟著縮小，會 GC 得更兇、更慢，
  尖峰再撞一下就 OOM。**這就是 `e2-small` 一定要加 swap 的原因。**

三種選法，擇一即可：

1. **`e2-medium`（4GB）** — 最省事，不必加 swap，建置也快。**建議這個。**
2. **`e2-small`（2GB）＋ 2GB swap** — 可行，建置會慢一些。
3. **`e2-small`（2GB），但不在主機上建置** — 在別的機器 `docker build` 後推映像到
   Artifact Registry，主機只負責跑。這樣 2GB 綽綽有餘。

> **關於作業系統版本**：app 與資料庫都跑在容器裡（`node:22-alpine`、`postgres:16`），
> 主機只要裝得動 Docker 就行，OS 版本幾乎不影響。寫 22.04+ 是因為那是驗證過的下限；
> 新開機器沒有理由不選 **24.04 LTS**（支援期最長）。

建立後先做三件事（`gcloud compute ssh` 進去之後）：

```bash
# 1. 系統更新
sudo apt update && sudo apt -y upgrade

# 2. 加 2GB swap——若選了 e2-small（2GB RAM），跑 next build 會 OOM，這一步不能省
#    選 e2-medium（4GB）可略過
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab

# 3. 安裝 Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER   # 重新登入後 docker 指令才不用加 sudo
```

**建置時要能連外**：`next build` 會向 `fonts.googleapis.com` / `fonts.gstatic.com` 抓字檔，
把 Noto Sans TC 與 Poppins 打包進產物（見 `src/app/layout.tsx`；這是 CSP `default-src 'self'`
之下唯一的做法，執行期不會再連外）。若建置環境擋掉這兩個網域，**build 仍會成功**、
但頁面會靜默退回系統預設字型——所以建置後請開首頁確認中文字看起來與官網一致。
（若主機端無法連外，改在能連外的機器 `docker build` 後推映像。）

**防火牆**：GCP 的預設 VPC 帶了一組寬鬆規則，要收掉。建立 VM 時勾「允許 HTTP／HTTPS 流量」
（會自動掛上 `http-server`、`https-server` 標記），SSH 則建議只從 IAP 進來：

```bash
# 只允許 Google IAP 的來源網段連 22，等於關掉對全世界開放的 SSH
gcloud compute firewall-rules create allow-ssh-from-iap \
  --network=default --allow=tcp:22 --source-ranges=35.235.240.0/20
# 刪掉預設那條「任何人都能連 22」的規則
gcloud compute firewall-rules delete default-allow-ssh
```

之後一律用 `gcloud compute ssh <VM 名稱> --zone=asia-east1-b --tunnel-through-iap` 連線。
資料庫的 5432 **不對外開放**——app 與 db 走 Docker 內部網路，compose 已把 app 綁在 `127.0.0.1:3000`。

**DNS**：在管理 `lhpedclinic.com.tw` DNS 之處新增 A 紀錄
`booking` → VM 的**靜態**外部 IP，等解析生效後再啟動 Caddy（憑證申請需要網域先指得到）。

### 2-1 部署步驟

前置：主機已照 §2-0 建好（Ubuntu 22.04+、已裝 Docker），
且網域 `booking.lhpedclinic.com.tw` 已指向主機的靜態 IP。
以下步驟與雲端商無關，換到別的主機也是同一套。

```bash
# 1. 取得程式碼（僅 booking-system 目錄即可獨立運作）
git clone <repo> && cd lihsin-clinic/booking-system

# 2. 設定環境變數
cp .env.example .env
#   - 產生密鑰：openssl rand -base64 48（三把各自不同）
#   - 設 POSTGRES_PASSWORD、APP_BASE_URL、LINE、簡訊帳號

# 3. 啟動（app + db + 每日備份 + 提醒排程）
docker compose up -d --build

# 4. 建立資料表與基礎資料
docker compose exec app npx prisma migrate deploy
docker compose exec app node node_modules/tsx/dist/cli.mjs prisma/seed.ts   # 測試環境
# 正式環境改用（不建立測試帳號）：
docker compose exec -e ADMIN_USERNAME=admin -e ADMIN_PASSWORD='安全密碼' \
  app node node_modules/tsx/dist/cli.mjs scripts/create-admin.ts

# 5. HTTPS 反向代理（擇一）。以 Caddy 為例（自動憑證）：
#   booking.lhpedclinic.com.tw { reverse_proxy 127.0.0.1:3000 }
```

首次登入後台後**必做**：
1. 修改管理員密碼（員工帳號頁）。
2. 啟用管理員兩步驟驗證（TOTP）。
3. 建立櫃檯人員帳號。
4. 依實際班表調整「排班管理」與「系統設定」（seed 預設兩位醫師全時段雙診）。

### 測試環境（正式上線前供診所人員試用）

另開一個目錄/主機用相同步驟部署，`.env` 使用**不同資料庫與密鑰**、`SMS_PROVIDER=console`、
LINE 用測試 channel 或留空。驗收表見 `docs/01`。正式與測試環境嚴禁共用資料庫。

## 三、備份與還原

### 自動備份

`docker compose` 內建 `backup` 服務：每日 03:30 `pg_dump -Fc` 到 `./backups/`，保留 30 天。

**這些 dump 存在 VM 自己身上，VM 掛了就一起沒了**，所以務必再同步一份到別的地方。
在 GCP 上最省事的是 Cloud Storage：

```bash
# 建一個 bucket（同樣放台灣），開啟版本控制，避免被覆寫或誤刪
gcloud storage buckets create gs://lihsin-backup --location=asia-east1 \
  --uniform-bucket-level-access
gcloud storage buckets update gs://lihsin-backup --versioning

# VM 用自己的服務帳戶就能寫入，不必另外放金鑰。加進 crontab
# （主機時區為 UTC，04:30 UTC = 台灣 12:30）
30 4 * * * gcloud storage rsync -r /path/booking-system/backups/ gs://lihsin-backup/booking/ >/dev/null
```

> VM 的服務帳戶要有這個 bucket 的 `roles/storage.objectAdmin`，而且建立 VM 時的
> 存取範圍要能用 Cloud Storage（預設的「允許預設存取權」即可）。

也可以同步到診所的 NAS——**放在診所裡的那一份最不怕雲端帳號出事**：

```bash
30 4 * * * rsync -a /path/booking-system/backups/ user@nas:/backup/lihsin-booking/
```

### 磁碟快照排程（GCP）

```bash
# 每天台灣 04:00（＝ 20:00 UTC）快照一次，保留 14 天
gcloud compute resource-policies create snapshot-schedule lihsin-daily \
  --region=asia-east1 --max-retention-days=14 \
  --daily-schedule --start-time=20:00 \
  --on-source-disk-delete=apply-retention-policy

# 掛到 VM 的開機磁碟上（磁碟名稱通常與 VM 同名）
gcloud compute disks add-resource-policies <磁碟名稱> \
  --zone=asia-east1-b --resource-policies=lihsin-daily
```

> **磁碟快照與這裡的 pg_dump 各救不同的事**：
> 快照救「整台機器壞掉」，dump 救「資料被誤刪、要回到某一天」。兩個都要。
> 而且兩者都在同一個 Google 帳號底下——**帳號本身出事就一起沒了**，
> 所以上面那份同步到診所 NAS 的 rsync 才是真正的最後一道。

### 每月必做：驗證備份還原得回來

備份檔存在，不代表還原得回來。每月挑一份 dump 實際還原到一個暫時的資料庫確認：

```bash
docker compose exec -T db psql -U lihsin -c "CREATE DATABASE restore_test;"
docker compose exec -T db pg_restore -U lihsin -d restore_test < backups/最新的.dump
docker compose exec -T db psql -U lihsin -d restore_test -c "SELECT count(*) FROM appointments;"
docker compose exec -T db psql -U lihsin -c "DROP DATABASE restore_test;"
```

筆數與當時的預約量相符即通過。這是整份備份計畫裡**唯一能證明它有效**的步驟。

### 手動備份

```bash
docker compose exec db pg_dump -U lihsin -Fc lihsin_booking > backups/manual_$(date +%Y%m%d%H%M).dump
```

### 還原

```bash
docker compose stop app reminder
docker compose exec -T db pg_restore -U lihsin -d lihsin_booking --clean --if-exists < backups/lihsin_booking_YYYYMMDD.dump
docker compose start app reminder
```

### ⚠️ 金鑰備份

`PII_ENCRYPTION_KEY`／`PII_HASH_KEY` 遺失＝證件號永久無法解密/比對。
請將 `.env` 離線影本（紙本或加密隨身碟）由院長保管；備份檔與金鑰**分開存放**。

## 五、個資保存與封存

- 預約與病人資料屬醫療掛號紀錄，預設保存；保存年限依診所個資政策（`privacy.retention_years` 設定，預設 3 年）。
- 到期封存做法：以備份 dump 冷存後，由管理員於資料庫執行匿名化腳本（將姓名/電話/證件密文以雜湊替代）；
  執行前務必先備份。此作業屬年度維護，建議由維護廠商或工程師執行。
